1. Zielsetzung

Dieser Plan beschreibt die Architektur und Umsetzung eines MCP-Servers (Model Context Protocol), der Support-Mitarbeitern den direkten Zugriff auf verschiedene Wissensquellen ermöglicht – ohne das Ticketsystem verlassen zu müssen.

Kernziele

  • Zentrale Wissensbasis: Support-Mitarbeiter greifen während der Ticketbearbeitung auf Wissensdatenbanken zu
  • Historische Daten nutzen: Das alte Ticketsystem wird als archivierte Datenquelle eingebunden
  • MCP-Standard: Das neue Ticketsystem kommuniziert per MCP-Protokoll mit dem Wissensserver
  • Multi-Source-Suche: Mehrere Wissenspools (Wiki, Runbooks, FAQ) werden zentral durchsuchbar
  • Externes FAQ: Ein Kunden-FAQ-Portal hinter Login wird für Supporter erschlossen

Ausgangssituation

SystemStatusHerausforderung
Altes Ticketsystem Wird abgeschafft Historische Daten müssen erhalten und durchsuchbar bleiben
Neues Ticketsystem Aktiv Muss MCP-Client integrieren oder per Plugin angebunden werden
Interne Wissensdatenbank Vorhanden Muss über Adapter an den MCP-Server angebunden werden
Externes FAQ-Portal Geplant Hinter Login – muss für Supporter erschlossen werden

3.3 Adapter — Altes Ticketsystem

Das alte Ticketsystem wird abgeschaltet. Die historischen Daten müssen exportiert und für die Suche erschlossen werden.

  1. Vollexport des alten Ticketsystems (CSV, SQL-Dump, JSON)
  2. Datenbereinigung und Normalisierung
  3. Import in eine Suchdatenbank (PostgreSQL / Elasticsearch)
  4. Read-only-Zugriff über den MCP-Server

Wichtiger Hinweis

Der Export dient ausschließlich der Referenz. Neue Tickets werden nur im neuen System erstellt. Es gibt keine Live-Synchronisation – der Export ist ein einmaliger Snapshot.

6. Externes FAQ-Portal

Konzept

Ein externes FAQ-Portal bietet Kunden selbstständige Hilfe zu häufigen Problemen. Das Portal liegt hinter einer Authentifizierung (Login-Bereich). Support-Mitarbeiter sollen dieses FAQ ebenfalls durchsuchen können – ohne sich separat einzuloggen. Der MCP-Server übernimmt die Authentifizierung transparent.

Anbindungsvarianten

VarianteBeschreibungVorteileNachteileEmpfehlung
A: REST-API FAQ-Portal bietet API für Suche Sauber, schnell, wenig Ressourcen API muss vom Portal bereitgestellt werden Beste Lösung
B: Headless-Browser Playwright crawlt die FAQ-Seiten Keine API nötig Langsam, wartungsintensiv Fallback
C: Regelmäßiger Export FAQ-Export (XML/JSON) wird importiert Einfach, performant Nicht tagesaktuell MVP-Phase

Empfohlenes Vorgehen

1

MVP: Export (Variante C)

Schnell umsetzbar, keine API nötig. Daten werden täglich importiert (max. 24h alt).

2

Optimierung: REST-API (Variante A)

Sobald das FAQ-Portal eine API bereitstellt, wird der Export durch Live-API ersetzt.

3

Stabilität: Hybrid (API + Export)

API als Primärquelle, Export als Fallback bei Nichterreichbarkeit.

7. Umsetzungsfahrplan

Übersicht – 11 Wochen

1

Basis · Woche 1–2

MCP-Server-Grundgerüst: Express + MCP-SDK + Auth + CI/CD + Docker + Deployment

Ergebnis: Lauffähiger MCP-Server mit Auth, aber ohne Datenquellen.

2

Wissensdatenbank · Woche 3–6

Datenmodell, PostgreSQL, kb_search/kb_get_article/kb_list_categories, Ticket-Export + Import, ticket_search_history/ticket_get_history

Ergebnis: Suche in Wissensdatenbank + historischen Tickets.

3

FAQ-Integration · Woche 7–9

Internes FAQ identifizieren, externes FAQ-Portal analysieren, faq_search/faq_search_external/solution_suggest

Ergebnis: Lösungsvorschläge aus allen Quellen.

4

Optimierung · Woche 10–11

Caching, Ranking, Audit-Log, Rate-Limiting, Monitoring, Lasttest, Rollout, Schulung

Ergebnis: Produktionsreifer MCP-Server mit Monitoring.
